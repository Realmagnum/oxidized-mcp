## 1. Цель

Предоставить ИИ-агенту (OpenCode) набор инструментов для быстрого и точного поиска настроек в конфигурациях сетевых устройств, хранящихся в Git-репозитории Oxidized. Ключевое отличие от «сырого grep» — понимание синтаксиса и структуры конфигов конкретных вендоров через систему плагинов.

## 2. Исходные условия

| Параметр | Значение |
|----------|----------|
| Хранилище | Git-репозиторий (стандартная установка Oxidized в Docker) |
| Масштаб | ~100 коммутаторов |
| Вендоры | D-Link, ELTEX, SNR |

## 4. Система плагинов вендоров

### 4.1. Интерфейс плагина

Каждый плагин реализует общий интерфейс:

```python
class VendorPlugin(ABC):
    name: str                    # "dlink", "eltex", "snr"
    match_patterns: list[str]    # как определить вендора по пути/имени файла

    def parse_config(self, raw: str) -> DeviceConfig
    def extract_vlans(self, raw: str) -> list[VLAN]
    def extract_acls(self, raw: str) -> list[ACL]
    def extract_ntp(self, raw: str) -> list[NTPEntry]
    def extract_snmp(self, raw: str) -> list[SNMPEntry]
    def extract_interfaces(self, raw: str) -> list[Interface]
    def extract_routing(self, raw: str) -> list[Route]
    def extract_lldp(self, raw: str) -> LLDPConfig
    def extract_mac_table(self, raw: str) -> list[MACEntry]
    def extract_voice_vlan(self, raw: str) -> list[VoiceVLAN]
    def extract_ssh(self, raw: str) -> SSHConfig
    def search(self, raw: str, entity: str, value: str) -> list[SearchHit]
```

### 4.2. Знания, зашитые в плагин

Плагин обязан содержать:
- **Словарь секций:** как разбить конфиг на логические блоки (VLAN, ACL, interface, routing, management, security).
- **Грамматические паттерны:** regex или конечные автоматы для извлечения параметров из строк конкретного вендора.
- **Нормализацию:** приведение извлечённых данных к единой pydantic-модели (общая схема `DeviceConfig`), чтобы ИИ-агент получал однотипный ответ вне зависимости от вендора.
- **Синонимы и альтернативные формы:** например, у D-Link VLAN создаётся через `create vlan`, а у SNR — `interface vlan`; оба варианта должны попадать в один результат.

### 4.3. Минимальный набор сущностей для извлечения (Фаза 1)

| Сущность | Что извлекаем |
|----------|---------------|
| VLAN | ID, name, tagged/untagged порты |
| Voice VLAN | ID, режим (auto/manual), порты, приоритет |
| ACL / Access-лист | Имя/номер, правила (permit/deny), направление, привязка к портам |
| NTP | Адрес сервера, источник |
| SNMP | Community, версия, разрешённые хосты |
| Интерфейсы | Имя, описание, статус, VLAN-привязка, port-security |
| Маршрутизация | Статические маршруты, default-route |
| LLDP | Глобальный статус, таймеры, состояние на портах |
| MAC-таблица (статика) | Статические MAC-записи, привязка к портам, VLAN |
| SSH | Статус сервера, версия, допустимые пользователи, ключи, ACL-привязка |

## 5. Инструменты MCP (Tools), доступные агенту

Каждый инструмент должен иметь подробное описание (`description`) в MCP-метаданных, чтобы агент понимал, когда и как его вызывать.

### 5.1. Основные (Фаза 1)

| Tool | Вход | Выход | Назначение |
|------|------|-------|------------|
| `list_devices` | vendor?, group? | Список `{hostname, vendor, group, ip, config_date}` | Обзор парка |
| `get_device_config` | hostname | Полный текст конфига + config_date | Просмотр целиком |
| `get_device_vlans` | hostname | Список VLAN (нормализованный) | Быстрый доступ к VLAN |
| `get_device_acls` | hostname | Список ACL | Быстрый доступ к ACL |
| `get_device_ntp` | hostname | Настройки NTP | Проверка синхронизации |
| `get_device_snmp` | hostname | Настройки SNMP | Проверка мониторинга |
| `get_device_interfaces` | hostname | Список интерфейсов | Состояние портов |
| `get_device_lldp` | hostname | Конфигурация LLDP | Проверка обнаружения соседей |
| `get_device_mac_table` | hostname | Статические MAC-записи | Проверка привязок |
| `get_device_voice_vlan` | hostname | Настройки Voice VLAN | Проверка телефонии |
| `get_device_ssh` | hostname | Конфигурация SSH | Проверка удалённого доступа |
| `search_across_devices` | entity, value, vendor? | Список совпадений по всем устройствам + config_date каждого | Глобальный поиск: «где настроен VLAN 200» |
| `raw_search` | regex, vendor? | Результат `git grep` с контекстом | Сырой поиск для нестандартных запросов |

### 5.2. Отметка времени конфигурации

Каждый ответ, содержащий данные устройства, **обязан** включать поле `config_date` — дату и время последнего коммита в Git для данного файла конфигурации.

```json
{
  "hostname": "sw-core-01",
  "vendor": "dlink",
  "config_date": "2026-09-01T14:32:07+03:00",
  "config_age_hours": 48.2,
  "vlans": [...]
}
```

**Получение:** `git log -1 --format=%cI -- <path_to_file>`.

Если возраст конфига превышает 24 часа, в ответ добавляется предупреждение `stale_warning: true`.

ИИ-агент может использовать это для принятия решений: «конфиг устарел, данные могут быть неактуальны».

### 5.3. Расширенные (Фаза 2 — история)

| Tool | Назначение |
|------|-----------|
| `get_config_history` | Список коммитов для устройства |
| `diff_configs` | Разница между двумя ревизиями |
| `find_recent_changes` | Что менялось за последние N дней |

**Архитектура Фазы 1 не должна блокировать добавление этих инструментов.**

## 6. Требования к эффективности для ИИ-агента

- **Описания инструментов (`descriptions`) — ключевое.** Каждый tool должен содержать:
  - Что делает.
  - Какие входные параметры принимает и их формат.
  - Пример вызова (в тексте описания).
  - Когда использовать, а когда — нет.
- **Компактный вывод.** Ответы должны быть структурированными (JSON), но без избыточности. Если конфиг 5000 строк, а агент ищет VLAN — не отдавать весь конфиг.
- **Ошибки — информативные.** Если устройство не найдено, вернуть список похожих имён. Если плагин не распознал вендор — сообщить, какой формат обнаружен.
- **Кэширование.** При ~100 устройствах допустимо кэшировать распарсенные конфиги в памяти с TTL (например, 5 минут) и инвалидацией по изменению файлов.
- **Определение вендора.** Автоматическое по имени файла, пути в Git-репозитории (группа в Oxidized) или содержимому. Приоритет: путь → содержимое.
- **Актуальность данных.** Поле `config_date` присутствует в каждом ответе. Агент всегда может оценить свежесть данных.

## 7. Работа с Git-репозиторием

- Сервер монтирует том с Git-репозиторием Oxidized (стандартный путь в Docker: `/srv/oxidized/configs` или переопределённый).
- Для чтения файлов используется прямое чтение из рабочей директории.
- Для глобального поиска — `git grep` или `grep -r` по рабочей директории (при ~100 устройствах оба варианта достаточно быстры).
- Для получения даты — `git log -1 --format=%cI -- <file>`.
- Сервер работает в режиме **только чтение**. Никаких записей в репозиторий.

| `test_parse_ntp` | Извлечение NTP-серверов |

**Требование:** каждый тест использует реальные конфиги (из `tests/fixtures/`), а не синтетические строки. Минимум 2 конфига на вендор (разные модели).

### 9.2. Интеграционные тесты MCP-инструментов

| Тест | Что проверяет |
|------|---------------|
| `test_list_devices` | Возвращает список с config_date |
| `test_get_device_config` | Полный конфиг + дата |
| `test_search_across_vlans` | Поиск VLAN 100 по всем устройствам |

| `test_unknown_device` | Несуществующее устройство → информативная ошибка |
| `test_cross_vendor_normalization` | Одинаковый запрос к D-Link и SNR → одинаковая структура ответа |

### 9.3. Запуск тестов

```bash

```

Все тесты должны проходить **без доступа к сети** и **без запущенного Oxidized**. Используются только файлы из `tests/fixtures/`.

## 10. Критерии приёмки (Фаза 1)

Агент может спросить:
- «На каких коммутаторах настроен VLAN 100?» → получает список устройств с указанием вендора, портов и `config_date`.
- «Покажи ACL на коммутаторе sw-core-01» → получает структурированный список правил.
- «Есть ли устройства без настроенного NTP?» → получает список.
- «Какие настройки SNMP на устройствах ELTEX?» → получает только по ELTEX.
- «Где включен LLDP и на каких портах?» → получает по устройствам.
- «Есть ли статические MAC-записи в VLAN 200?» → получает список привязок.
- «На каких коммутаторах настроен Voice VLAN?» → получает список с параметрами.
- «У каких устройств SSH-доступ не ограничен ACL?» → получает список потенциально опасных конфигураций.
- «Когда последний раз обновлялся конфиг на sw-access-15?» → получает `config_date`.

Вывод структурированный, компактный, без «мусорных» данных.

Плагины изолированы: добавление нового вендора = добавление одного файла в `plugins/` без изменения ядра.

Время ответа на любой запрос < 2 секунд (при ~100 устройствах).

Все тесты из раздела 9 проходят успешно.

## 11. Расширение поддерживаемых устройств

### 11.1. Руководство по добавлению нового вендора

Для добавления нового вендора необходимо:
1. Собрать примеры конфигов (минимум 2–3 файла разных моделей) и поместить в `tests/fixtures/<vendor>/`.
2. Создать файл плагина `src/plugins/<vendor>.py`, наследующий `VendorPlugin`.
3. Реализовать методы извлечения для каждой сущности из раздела 4.3.
4. Добавить паттерны определения вендора (по имени файла, группе, содержимому).
5. Написать тесты по образцу существующих.
6. Зарегистрировать плагин в `src/plugins/__init__.py` (одна строка).

### 11.2. Чек-лист для нового плагина

- [ ] Конфиги разных моделей одного вендора парсятся корректно.
- [ ] Все сущности из раздела 4.3 извлекаются (или метод возвращает пустой список с комментарием «не поддерживается данной моделью»).
- [ ] Нормализованный вывод совпадает по структуре с другими вендорами.
- [ ] Тесты покрывают минимум 2 модели.
- [ ] `match_patterns` не конфликтуют с существующими плагинами.

### 11.3. Приоритетные кандидаты на расширение

| Вендор | Обоснование |
|--------|-------------|
| Cisco (IOS/IOS-XE) | Широкая распространённость, синтаксис часто является референсным |
| Huawei (VRP) | Распространён в операторских сетях |
| Juniper (Junos) | Отличается структурой (иерархический формат), потребует адаптации парсера |
| MikroTik (RouterOS) | Экспорт в формате `/export`, отличается от классического CLI |

## 12. Ограничения и допущения

- Фаза 1 работает только с текущим состоянием конфигов.
- Сервер не взаимодействует с устройствами напрямую — только читает бэкапы Oxidized.
- Конфиги предполагаются в текстовом формате (стандартный вывод Oxidized).
- Плагин для вендора разрабатывается на основе реальных примеров конфигов (не менее 2–3 примеров на вендор для тестов).
- Поле `config_date` является **обязательным** в каждом ответе. Отсутствие даты трактуется как ошибка.
